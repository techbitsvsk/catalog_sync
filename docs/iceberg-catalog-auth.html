1. Local stack — what each service does

Seven containers. Nessie is not exposed to the host — all client traffic goes through the catalog-gateway (port 8083), which is the sole enforcement point. MinIO never knows about table schemas — it only stores bytes.

Key separation: Nessie stores a pointer (metadataLocation: s3a://warehouse/gold/orders/metadata/v3.metadata.json). It never reads or writes Parquet files. The catalog-gateway is the sole client entry point — it validates JWTs, enforces OPA policy, and forwards to Nessie with its own admin token. Clients never speak to Nessie directly.

2. What Iceberg actually stores — the metadata chain

Every Iceberg table is a chain of immutable files. Each layer references the one below it using absolute S3/GCS/ADLS URIs embedded in the file content itself. This is why copying files without rewriting the chain produces a broken table.

Why iceberg-sync rewrites the chain: When copying from Azure ADLS to MinIO, every URI in metadata.json, manifest-list.avro, and manifest.avro must change from abfss://container@account.dfs.core.windows.net/… to s3a://warehouse/…. Only then is the table readable from the new location. The Parquet files themselves do not embed their own path, so they need no modification.

How Iceberg scan planning uses column statistics

Each manifest row carries lower_bounds and upper_bounds per column, copied from the Parquet file footers. When a query has a predicate like region = 'EMEA', Iceberg compares it against these bounds before opening any file:

flowchart LR PRED["Predicate\nregion = 'EMEA'"] ML["Manifest list\n2 manifests"] M1["Manifest m-001\nlower=EMEA upper=EMEA"] M2["Manifest m-002\nlower=APAC upper=APAC"] SKIP["SKIP\n(APAC ≠ EMEA)"] OPEN["OPEN file\nemea-001.parquet"] PRED --> ML ML --> M1 ML --> M2 M1 -->|"EMEA overlaps EMEA"| OPEN M2 -->|"APAC cannot contain EMEA"| SKIP style SKIP fill:#2d1a1a,stroke:#f87171 style OPEN fill:#1a2d1a,stroke:#34d399
This is what structured scan expressions unlock in the catalog gateway. When the gateway converts the OPA row_filter to a structured Iceberg expression ({type: eq, term: region, value: EMEA}), Nessie can push the predicate into scan planning — skipping entire Parquet partition files before reading a single row. The gateway's _sql_to_iceberg_expr() handles this conversion automatically; unsupported predicates are logged and skipped (fail-open for that filter).

3. Nessie as a catalog — what it stores vs MinIO

Nessie is a transactional metadata store — think Git for table definitions. It does not touch object storage. Its job is to atomically record which metadataLocation is the current version of each table, on each branch.

flowchart LR subgraph NESSIE_STORE["Nessie (PostgreSQL backend)"] direction TB MAIN["main branch\n─────────────────────────\ngold.orders → v3.metadata.json\ngold.customers → v1.metadata.json\nsilver.events → v7.metadata.json"] DEV["dev branch\n─────────────────────────\ngold.orders → v4.metadata.json\n(schema evolution in progress)"] MAIN -.->|"branched from"| DEV end subgraph MINIO_STORE["MinIO (object storage)"] direction TB V3["v3.metadata.json\n(current on main)"] V4["v4.metadata.json\n(current on dev)"] MAN["manifests + parquet\n(shared between branches\nwhere data is unchanged)"] V3 --- MAN V4 --- MAN end NESSIE_STORE -->|"metadataLocation pointer\n(Nessie only stores the path,\nnever the file content)"| MINIO_STORE

Optimistic concurrency: Nessie's commitTable uses a compare-and-swap on the commit hash. If two writers race, the second writer gets a 409 Conflict and must retry (re-read, re-apply, re-commit). This is how Iceberg achieves snapshot isolation without locks.

4. OAuth2 token flow — issuing and validating JWTs

The oauth-service is a full OAuth 2.0 Authorization Server implementing RFC 6749 client credentials grant and RFC 7517 JWKS. Nessie acts as a Resource Server — it never issues tokens, only validates them.

The private key never leaves the oauth-service container. Nessie only ever sees the public key (via JWKS). Even if Nessie's PostgreSQL database were compromised, an attacker could not forge new tokens — they would need the RSA private key stored in the oauth-service's database.

5. BEARER approach — why it breaks at token expiry

BEARER (static token)

  • Fetch token manually with requests.post()
  • Pass it via spark.conf.set("…authentication.token", token)
  • Token expires in 3600 s → gateway starts returning 401
  • Switching principals = call spark.conf.set() again, but the already-initialized RESTCatalog instance has cached the old identity — requests may still use the old token
  • Long-running jobs silently fail mid-job when the token expires

OAUTH2 (Iceberg RESTCatalog manages tokens)

  • Configure credential = client_id:client_secret + oauth2-server-uri in catalog config
  • RESTCatalog fetches token on first catalog call via client_credentials grant
  • Checks expiry before every API call — refreshes automatically when exp - now < buffer
  • Per-principal identity = one named catalog per identity, each isolated with its own token lifecycle
  • Long-running jobs just work — refresh is transparent

6. Spark RESTCatalog — catalog-per-principal via gateway

Each named catalog in the SparkSession is an independent Iceberg RESTCatalog instance with its own OAuth2 credentials. All traffic goes through catalog-gateway:8083 — not directly to Nessie. The gateway validates the JWT, enforces OPA policy, and forwards using its own admin token. Enforcement is transparent to Spark.

7. Full query lifecycle — gateway-enforced read

Putting it all together: what happens between spark.table("gw_analytics.gold.orders") and the enforced DataFrame appearing in your application. No application-level filter calls — the gateway enforces transparently.

Infrastructure-enforced, not advisory. The gateway injects the scan filter expression before Nessie responds — Nessie returns only EMEA partition files (file-level pruning). Spark never receives a schema with ssn or credit_card_number, so it cannot project or request those columns. No application cooperation required.

8. Other query engines — Trino, Flink, PyIceberg, DuckDB

Every engine connects to catalog-gateway:8083 (Iceberg REST Catalog protocol). The gateway enforces OPA policy for all engines — no engine-specific policy integration needed. All engines authenticate with the same OAuth2 client credentials flow.

9. OPA policy enforcement — infrastructure-level

The catalog-gateway is an enforcing proxy, not an advisory sidecar. All Iceberg REST traffic passes through it. OPA evaluates every request. Nessie port 19120 is not exposed to the host — bypassing the gateway is a network-level impossibility, not an application convention.
